# 6. Troubleshooting case studies

| **Case 1**                  | **Detail**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
|-----------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Scenario                    | A new PC on the staff VLAN (10.10.10.0/24, gateway 10.10.10.1) is given a static address of 10.10.10.70 but with the mask of 255.255.0.0 (/16) instead of 255.255.255.0.                                                                                                                                                                                                                                                                                                                                                                                                           |
| Symptoms                    | The PC can browse the internet and reach colleagues on the same VLAN but cannot reach the internal servers at 10.10.20.x. Other staff PCs reach those servers without trouble.                                                                                                                                                                                                                                                                                                                                                                                                     |
| Diagnostic steps (in order) | 1. Compare with a working PC – only this one fails so suspect the host, not the network. 2. Ping the gateway, which works, so layer 2 and the VLAN are fine. 3. Ping the server 10.10.20.10 which times out. 4. Check the address settings and see the /16 mask 5. Check the ARP table, which shows an incomplete entry for 10.10.20.10, meaning the PC tried to find the server directly instead of going via the gateway. 6. Apply the mask by hand: 10.10.20.10 AND 255.255.0.0 gives 10.10.0.0, the same network as the PCs own, so the PC wrongly treats the server as local. |
| Root cause                  | The mask is too short. The PC believes everything in 10.10.0.0/16 is on its own subnet, so it sends an ARP broadcast for the server instead of sending the packet to the gateway. The broadcast cannot leave VLAN 10 (see 3.1), so nobody answers. Internet addresses are outside 10.10.x.x, so they still go via the gateway, which is why browsing works.                                                                                                                                                                                                                        |
| Fix                         | Set the mask to 255.255.255.0, or switch the PC to DHCP. Clear the ARP cache and retest the ping.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| How to prevent it           | Use DHCP for ordinary devices so masks come from one place. Where static addresses are needed, take them from the addressing plan (4.4), and check each address, mask and gateway before connecting the device.                                                                                                                                                                                                                                                                                                                                                                    |

| **Case 2**                  | **Detail**                                                                                                                                                                                                                                                                                                                                                                                                                                           |
|-----------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Scenario                    | A second switch in a meeting-room cabinet is connected to the main switch by a trunk. A Wi-Fi access point on it is placed in VLAN 30 (Guests, 10.10.30.0/24). The trunk was set up before VLAN 30 existed and still allows only VLANs 10 and 20.                                                                                                                                                                                                    |
| Symptoms                    | Visitors can join the Guest Wi-Fi, but receive no usable address (a self-assigned 169.254.x.x address) and get no internet. Staff and server VLANs on both switches work normally. Guests plugged into the main switch work normally.                                                                                                                                                                                                                |
| Diagnostic steps (in order) | \(1\) Note the pattern: only VLAN 30, only on the second switch. (2) Check the access point's port is in VLAN 30 on the second switch, which it is. (3) Check VLAN 30 exists on both switches. (4) Check the trunk's allowed VLAN list (for example, with show interfaces trunk on a Cisco switch) and see that it contains 10 and 20 but not 30. (5) Conclude the guests' DHCP requests are being dropped at the trunk and never reach the gateway. |
| Root cause                  | The trunk's allowed list does not include VLAN 30, so frames tagged for VLAN 30 are not carried between the switches (see 3.1 on trunk ports and 802.1Q).                                                                                                                                                                                                                                                                                            |
| Fix                         | Add VLAN 30 to the allowed list on both ends of the trunk, using the "add" form of the command so the existing VLANs are kept (replacing the list instead would cut off VLANs 10 and 20). Then renew a guest device's address and confirm it receives 10.10.30.x.                                                                                                                                                                                    |
| How to prevent it           | Add "update every trunk" to the checklist for creating a VLAN, record each trunk's allowed list in the network documentation, and test from a device on the far switch after every VLAN change.                                                                                                                                                                                                                                                      |

| **Case 3**                  | **Detail**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Scenario                    | During a tidy-up of the firewall rule table from 5.4, the broad rule denying the DMZ (10.10.40.0/27) access to the internal networks is moved above the narrow rule allowing the web server (10.10.40.10) to reach the database (10.10.20.10) on TCP 5432.                                                                                                                                                                                                                                                                                                                                                                                          |
| Symptoms                    | The public website still loads and static pages display, but pages that need data, such as search and login, hang or show an error. The database server is running and Staff can reach it normally.                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Diagnostic steps (in order) | \(1\) Confirm the front-end works: HTTPS to the web server succeeds, so rule 2 is fine. (2) Check the web server's application log, which shows database connection timeouts. (3) From the web server, test a connection to 10.10.20.10 on port 5432, which fails while the same test from a Staff PC succeeds, so the database is healthy and the path from the DMZ is the problem. (4) Check the firewall log, which shows repeated drops from 10.10.40.10 to 10.10.20.10:5432, attributed to the DMZ deny rule. (5) Read the rule list in order, see the deny above the allow, and check hit counters: the deny is rising, the allow shows zero. |
| Root cause                  | The firewall uses first-match processing (see 5.3). The broad deny matches the database traffic first, so the narrower allow beneath it is never reached. It is a shadowed rule.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Fix                         | Move the allow rule back above the deny, then retest from the web server and confirm the pages load. Watch the log to confirm drops from that source have stopped.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| How to prevent it           | Always put specific rules above general ones, review rule order after every change, check hit counters for rules that never match, comment every rule with its purpose, and test the real application after changes, not only whether the firewall accepted the configuration.                                                                                                                                                                                                                                                                                                                                                                      |

| **Case 4**                  | **Detail**                                                                                                                                                                                                                                                                                                                                                                                                |
|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Scenario                    | In Figure 1, a static route is added on Router A for the Branch network (192.168.20.0/24) via the WAN link. Nobody adds the matching route on Router B for Head office (192.168.10.0/24).                                                                                                                                                                                                                 |
| Symptoms                    | A ping from PC 1 (LAN A) to PC 3 (LAN B) times out. Each LAN works internally, and each router can ping the other's WAN address. A traceroute from PC 1 shows Router A at hop 1 and then only timeouts.                                                                                                                                                                                                   |
| Diagnostic steps (in order) | \(1\) Test outwards in stages: PC 1 to its gateway works, PC 1 to Router A's WAN address works, PC 1 to Router B's WAN address works. (2) Ping PC 3, which fails. (3) Look at Router A's routing table, which has a route to 192.168.20.0/24. (4) Look at Router B's routing table, which has no route to 192.168.10.0/24. (5) Realise the requests probably reach PC 3 but the replies have no way back. |
| Root cause                  | Routing must work in both directions. Router A knows how to reach LAN B, but Router B has no route back to LAN A, so replies are dropped or sent the wrong way (see 2.2 on routers linking LANs across a WAN).                                                                                                                                                                                            |
| Fix                         | Add a route on Router B for 192.168.10.0/24 via Router A's WAN address, or a default route if the branch only needs to reach Head office and the internet. Retest from both ends.                                                                                                                                                                                                                         |
| How to prevent it           | Treat every new route as a pair and check both directions after any change. Use a dynamic routing protocol such as OSPF where there are several sites, so routes are shared automatically. Test with a ping in each direction before declaring the link live.                                                                                                                                             |
